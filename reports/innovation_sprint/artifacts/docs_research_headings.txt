23:## T1) Optional Delta Index + Watchers + Planner
25:- Core idea: maintain an optional local delta index (postings + path map) using filesystem watchers and route most queries to index lookup instead of full walk+grep.
26:- Math foundation: cost-constrained optimization. Maximize `E[success@k,t] - lambda*latency` under stage-cost budget with a fallback constraint.
27:- Systems mechanism: journal events update index incrementally; query planner executes `index lookup -> confidence test -> fallback scan only if needed`, removing walk and broad scan from hot path.
28:- Integration points: `CandidateGenerator::build_index`, `CandidateGenerator::generate`, `CandidateGenerator::generate_streaming`, `search_progressive` in [progressive.rs](/C:/Users/pablo/Downloads/Ixos/src/ixos_rank/progressive.rs).
29:- Telemetry needed: index hit-rate, stale-hit rate, fallback frequency, opened-file@k-in-time, TTFR/Total stage ms. Privacy degradation: disable persistence in journalist mode and run session-only index.
30:- Evaluation plan: baseline Ixos vs recency-scope heuristic vs T1. Stratify by cold/warm cache and high-churn repos. Primary metrics: TTFR p95, Total p95, opened-file-in-top-k within 1s/2s.
31:- Novelty audit:
32:- Windows Search indexing docs and Spotlight docs show indexing pattern but not Ixos-style progressive cascade + privacy fallback.
33:- Watchman/inotify/USN docs show watcher mechanics, not retrieval planner design.
34:- Lucene NRT explains incremental index serving, not local-first progressive file-search constraints.
35:- Honest risks: index staleness and watcher drop events can hurt recall. Fails under rapid mass rename unless fallback scan is robust.
37:## T2) Trigram/Bloom Scan Elimination Layer
39:- Core idea: build lightweight trigram postings and Bloom sketches so ripgrep runs only on plausibly matching files.
40:- Math foundation: probabilistic filtering; optimize false-positive rate `p` vs CPU/memory to minimize expected scan cost.
41:- Systems mechanism: `query -> trigram candidate file set -> Bloom confirmation -> ripgrep only on survivors`; cut scan fanout and downstream embedding/ranking workload.
42:- Integration points: `ripgrep_funnel` and candidate merge path in [mod.rs](/C:/Users/pablo/Downloads/Ixos/src/ixos_rank/candidate_generator/mod.rs), semantic stage in [semantic_engine.rs](/C:/Users/pablo/Downloads/Ixos/src/ixos_rank/semantic_engine.rs).
43:- Telemetry needed: filter pass rate, false-negative audits, scan bytes avoided, candidate quality at K. Privacy degradation: sketches can be session-only in deep-search.
44:- Evaluation plan: compare no-filter, trigram-only, trigram+Bloom. Evaluate high-entropy vs low-entropy query classes.
45:- Novelty audit:
46:- Russ Cox trigram indexing and Zoekt already show trigram speedups.
47:- Everything/Code-search systems use prefiltering patterns.
48:- Ixos contribution would be integration with progressive stream + privacy-mode switch.
49:- Honest risks: false negatives if tokenizer mismatch is wrong. Fails on very short/regex-like queries unless bypass rules exist.
51:## T3) Learned Cost-Based Query Planner
53:- Core idea: learned planner chooses stage sequence and budgets per query (`walk/scan/embed/rank`) using predicted gain-per-ms.
54:- Math foundation: constrained Markov decision process / cost-based policy optimization.
55:- Systems mechanism: pre-query feature extraction (query stats, repo stats, cache state), then choose one of several plans; expensive stages are skipped when marginal gain is low.
56:- Integration points: `ProgressiveSearchConfig`, `search_progressive`, `should_refine`, mode resolution in [search.rs](/C:/Users/pablo/Downloads/Ixos/src-tauri/src/commands/search.rs).
57:- Telemetry needed: predicted vs realized latency, plan regret, quality delta, fallback-trigger rate. Privacy degradation: planner runs with non-personal features when privacy mode is on.
58:- Evaluation plan: baseline static pipeline vs hand heuristic planner vs learned planner. Add regret and SLA violation metrics.
59:- Novelty audit:
60:- System R (classical CBO), Neo, Bao establish learned planning foundations.
61:- Retrieval literature has stage-aware heuristics but less local-desktop privacy framing.
62:- Novelty should be phrased as local-progressive constrained planning, not optimizer novelty.
63:- Honest risks: policy drift and unstable plans. Fails if offline labels are not representative.

76:- Prior art means no "first" claim; claim should be risk-controlled cascade for local file search.
77:- Honest risks: bad calibration on rare queries. Fails if nonstationary workloads drift without recalibration.

88:## Candidate A - Probe-Miss Risk Certificate Planner (PMRCP)
90:### Core object (formal definition)
93:- Query `q`
94:- Stage set `S = {path, lexical, semantic, evidence}`
95:- Action budget vector `b = (b_1, ..., b_|S|)`
96:- Probe family `P(q) = {p_1, ..., p_m}` (cheap lexical/path probes)
97:- Risk target `alpha` and recall target `tau`
100:- Plan `pi(q)` deciding stage effort under budget
101:- Certificate `C(q) = (L_recall, alpha, tau, cost)` where `L_recall` is a lower confidence bound
104:- Minimize expected latency `E[T(pi)]`
105:- Subject to `Pr(Recall@K < tau) <= alpha`
107:### Math intuition
109:- Use probe outcomes as sequential evidence of miss-risk.
110:- Maintain an anytime-valid lower bound `L_t` on recall under current explored scope.
111:- Escalate expensive stages only when `L_t < tau`.
112:- Stop/de-escalate when certificate is strong enough.
114:### Mechanism for BIG speedup
116:- Removes expensive downstream work on low-risk queries.
117:- Converts fixed heavy processing into selective processing.
118:- Directly reduces file touches, scans, embedding calls, and rerank operations.
122:## Candidate B - Anytime Top-k Stability Certificate (ATSC)
124:### Core object (formal definition)
127:- Progressive candidate stream
128:- For document `d` at step `t`: score interval `[l_d(t), u_d(t)]`
129:- Cutoff `k`, confidence `1-delta`
132:- Stop flag `S_t` meaning top-k is stable with confidence `1-delta`
135:- Let `theta_k(t)` be kth largest lower bound among current top-k.
136:- Let `U_rest(t)` be max upper bound over non-top-k / unseen items.
137:- Stop when `theta_k(t) - U_rest(t) > beta_t(delta)`.
139:### Math intuition
141:- `beta_t(delta)` from concentration or anytime confidence sequences.
142:- Once the gap exceeds uncertainty margin, rank inversion probability is bounded.
144:### Mechanism for BIG speedup
146:- Terminates long-tail candidate expansion and rerank early.
147:- Avoids unnecessary late-stage compute once rank outcome is statistically stable.
151:## Candidate C - Certified Mandatory-Anchor Signature (CMAS)
153:### Core object (formal definition)
156:- `S_f = (E_f, B_f, h_f)`
157:- `E_f`: exact compact set for rare mandatory anchors
158:- `B_f`: probabilistic sketch for broader token presence
159:- `h_f`: optional tiny similarity hash
162:- `g(q, S_f) -> {reject, uncertain, pass}`
165:- Zero false negatives for mandatory rare anchors represented in `E_f`.
166:- Bounded false-positive rate for sketch checks in `B_f`.
167:- "Uncertain" path prevents unsafe hard rejection.
169:### Math intuition
171:- Mandatory rare anchors are checked exactly from `E_f`.
172:- Non-rare anchors use bounded-error membership via `B_f`.
173:- Expected scan reduction follows from reject/pass/uncertain distribution.
175:### Mechanism for BIG speedup
177:- Eliminates most file opens and ripgrep scans before expensive parsing/semantic stages.
178:- Fits no-global-DB rule: tiny per-file token in xattr/ADS/flat metadata, optional daemon memory cache.
